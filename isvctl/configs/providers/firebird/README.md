# Firebird Provider Configs

Firebird is a bare-metal and VPC cloud control plane. Tenants manage their resources through a REST API under `/api/v1`, authenticated with tokens from the platform's OIDC issuer. Bare-metal servers (BMs) are pre-allocated to a tenant rather than created on demand: a run attaches one of the tenant's BMs to a project and a tenant subnet, provisions an OS image on it, and releases it again. Network resources are managed through the API. A rule counts as observed when its Operation completes and its readback is READY; this measures control-plane completion, not traffic propagation. Filesystems are served by a parallel filesystem in which each tenant has its own organization. Mutations return asynchronous Operations that complete once the platform has applied them.

Every config needs service-account credentials (or a bearer token) and a project (see [Environment](#environment) and [Credentials](#credentials)). The control-plane, iam, and security configs talk only to the API, and so does the storage config unless it is given a provisioned BM to mount filesystems on. The bare_metal config, and the network and image-registry configs with `--capability bare_metal`, also need an OS image, an `AVAILABLE` BM in the tenant pool, and a network path from the host running isvctl to the tenant subnet (BM addresses are private), because they SSH into the provisioned BM. The network config's connectivity, traffic, and scoping checks additionally need a peer BM in the same VPC.

These provider configs wire the [provider-agnostic test suites](../../suites/README.md) to that API ([scripts](scripts/)). Scripts are stdlib-only and share one API client, [`scripts/common/firebird_client.py`](scripts/common/firebird_client.py).

## Lifecycle model

Firebird BMs are tenant-owned, pre-allocated servers - they are never created or deleted.

- **create_network** passes a supplied `FIREBIRD_SUBNET_ID` (with its `FIREBIRD_VPC_ID`) through untouched. Without one it creates a subnet - inside `FIREBIRD_VPC_ID` when given, otherwise inside a new VPC - and **teardown_network** deletes exactly what it created (subnets first, then the VPC), after the BM has been detached. Creating a VPC or subnet is an API call. Network resources are managed through the API; a rule counts as observed when its Operation completes and its readback is READY, which measures control-plane completion, not traffic propagation.
- **launch** attaches a BM to the project and subnet (only if needed), then provisions an OS image. Automatic selection only considers `AVAILABLE` BMs that are in no other project and on no other subnet. The SSH key is generated per run in a fresh private directory (`tempfile.mkdtemp`, mode `0700`) and injected through cloud-init user-data; launch reports it as `key_file` with `generated_key: true`.
- **teardown** undoes only what launch did: it deprovisions (wipes the OS) a BM that launch provisioned or was told to reuse, and detaches only what launch attached. Before detaching a subnet the run attached, it deletes the BM's DHCP reservation on that subnet and waits until the reservation is gone, because the API refuses the detach (409) while the BM still holds one; a BM whose subnet the tenant had attached keeps its reservation. A BM that launch rejected (for example, one already `RUNNING`), or whose provision request the API refused, is never touched. It deletes only a key the run generated; a key supplied with `BM_KEY_FILE` is kept.

VPC/subnet create and delete, subnet attach/detach, power, provision, and deprovision actions return an asynchronous Operation; the client polls it to completion and then waits for the BM readback to reflect the new state. Project attach/detach are synchronous.

- **Readiness.** SSH answers before cloud-init's final modules finish, so launch also waits for `cloud-init status` to leave its running state and reports it as `cloud_init_status`.
- **cloud-init check (BOOT02-01).** User-data arrives on a config drive and no link-local metadata service is served, so `metadata_service` fails on every run. The provider config runs the check in the test phase, where that subtest still fails but no longer skips every test-phase check.
- **Power-on after power-off.** The BMC can refuse a power-on while the host is still shutting down, and the platform applies it once the host is off. `start_instance` records a failed power-on Operation as `power_on_operation_error` and judges the step by the BM readback: it fails only if the BM does not reach RUNNING.

|----------|----------|-------------|

The variables are registered with `isvctl configure --provider firebird` (persisted under `firebird:`; the client secret and bearer token go to `secrets.yml`) and `isvctl doctor`.

### Credentials

- **bare_metal** needs tenant-scope BM read, such as tenant ADMIN: BM selection lists the tenant pool (`GET /compute/bms`), which a project-scoped role cannot read.
- **image-registry** needs tenant-scope image create for the upload (finishing an upload registers the image), plus the bare_metal scope for the BM install - tenant ADMIN covers both.
- **control-plane, iam, security** need tenant ADMIN (see [Service accounts](#service-accounts-control-plane-iam-security)).

## Quick Start

```bash
uv run isvctl test run -f isvctl/configs/providers/firebird/config/bare_metal.yaml
```

BM IPs are on the tenant subnet and are not internet-routable. Run isvctl on a host that can reach that subnet (over VPN, or from a shell on a jump host in that network) so the SSH-based host, GPU, and workload checks can connect. `isvctl deploy run` does not forward `FIREBIRD_*` variables, so export them on whichever host runs isvctl.

The image must boot Ubuntu with NVIDIA drivers and a GPU-enabled container runtime, and apply cloud-init user-data (the SSH key is injected that way for its default user, `ubuntu` unless `FIREBIRD_SSH_USER` says otherwise). GPU checks inherit the suite's expectation of 8 GPUs per node.

Dev workflow: `BM_SKIP_TEARDOWN=true` keeps the BM provisioned (and any network the run created, and the run's generated key); later runs reuse it with `BM_INSTANCE_ID` and `BM_KEY_FILE` set to the `key_file` that run's `launch_instance` reported (for example `/tmp/isv-bm-test-gpu-abc123/isv-bm-test-gpu-key`), and a reuse run without `BM_SKIP_TEARDOWN` deprovisions it at the end (attachments made by the first run stay in place, and the supplied key is not deleted - remove its directory yourself when done). A key is reused only when supplied that way; no run picks up a key file it did not generate. A reuse run must set `FIREBIRD_VPC_ID` / `FIREBIRD_SUBNET_ID` to the BM's network; `teardown_network` prints both IDs when it keeps a created network, and that network is then yours to delete.

## Network suite

```bash
uv run isvctl test run -f isvctl/configs/providers/firebird/config/network.yaml
# include the BM checks (DHCP, stable IPs, fabric, connectivity, traffic):
BM_INSTANCE_ID=bm.xxx BM_KEY_FILE=<key_file of a kept bare_metal run> \
  uv run isvctl test run -f isvctl/configs/providers/firebird/config/network.yaml --capability bare_metal
```

- **Network lifecycle.** `create_network` creates a VPC with two subnets (`FIREBIRD_NETWORK_VPC_CIDR`, `FIREBIRD_NETWORK_SUBNET_CIDR_A` / `_B`; default `172.16.243.0/24` split into two `/25`s) and `teardown` deletes exactly those. With `FIREBIRD_NETWORK_VPC_ID`, `FIREBIRD_NETWORK_SUBNET_ID_A`, and `FIREBIRD_NETWORK_SUBNET_ID_B` set it passes that network through and creates and deletes nothing (supply both subnets: `NetworkProvisionedCheck` needs two); with only `FIREBIRD_NETWORK_VPC_ID` it creates the two subnets inside that VPC. `NETWORK_SKIP_TEARDOWN=true` keeps a created network, and teardown prints the three IDs to set for the next run. `vpc_crud` creates and deletes a short-lived VPC of its own, with no subnet (`FIREBIRD_CRUD_VPC_CIDR`; default `172.16.241.0/24`). The API rejects a CIDR that overlaps another VPC or subnet in the project, so every default across both configs is disjoint - including bare_metal's `172.16.240.0/24`, which a bare_metal run kept with `BM_SKIP_TEARDOWN=true` leaves in place. Override one only with another unused range. Every firewall rule a step creates is deleted by that step on every path; rules are named `isv-*`, so a run killed mid-step leaves only rules with that prefix to clean up.
- **VLANs.** Every subnet created takes a VLAN from the tenant's pool, so a network run that creates its network uses two and a bare_metal or image-registry run that creates one uses one. Only `create_network` creates subnets. Reuse a kept network where possible: `FIREBIRD_NETWORK_VPC_ID` / `FIREBIRD_NETWORK_SUBNET_ID_A` / `_B` for the network config, `FIREBIRD_VPC_ID` / `FIREBIRD_SUBNET_ID` for bare_metal and image-registry.
- **Security groups are firewall rules.** Firebird has no security-group object; a VPC's firewall rules are its policy. `sg_crud` maps create/read/add/modify/remove/delete onto the lifecycle of the rules it creates in the run's VPC (see the script docstring); `create_vpc` is that VPC reading back READY, since the step creates no network. Rules the VPC already had are left alone.
- **Probe-rule shape.** `sg_crud`, `sg_policy_propagation`, and `sdn_filter_audit_trail` create their rules in the run's VPC (`create_network`'s, created or supplied) and never create or delete a VPC or subnet. Two constraints shape those rules. Where the API does not check them at request time, it accepts the rule and its Operation then fails:
  - Some deployments reject a TCP or UDP rule without a source port range. Sending the full range is equivalent, so every TCP rule the provider creates sends `srcPortFrom=1`, `srcPortTo=65535` (`tcp_rule` in `scripts/common/network.py`).
  - A rule whose prefixes are both outside every subnet of the VPC is rejected. A prefix inside the VPC CIDR but outside every subnet counts as outside. Current API versions reject such a rule at request time (HTTP 400 `VALIDATION_ERROR`, no Operation); older ones accept it and the Operation fails. So each probe rule matches TCP from TEST-NET-1 (`192.0.2.1/32`, RFC 5737) to one `/32` inside subnet A (its last usable host). No real traffic comes from TEST-NET-1, so the rules affect none, even if a host holds that address.
- **VPC update is not supported.** Firebird VPCs have no tags or DNS settings, so `vpc_crud` reports `update_tags` / `update_dns` failed as not supported and `VpcUpdatedCheck` fails; create, read, and delete are checked normally.
- **Propagation and audit.** `sg_policy_propagation` times a rule's create and delete until the Operation completes and the readback agrees (control-plane evidence; the threshold is 10 s). `sdn_filter_audit_trail` finds the rule's CREATE/UPDATE/DELETE events in `GET /audit` and skips when the audit API is disabled.
- **Provisioned BMs.** The network suite does not provision BMs. The BM checks use an already-provisioned BM (`BM_INSTANCE_ID` + `BM_KEY_FILE`, for example one kept by a bare_metal run with `BM_SKIP_TEARDOWN=true`) and skip without one; `stable_ip_test` powers it off and on. `connectivity_test`, `traffic_validation`, `sg_node_scoping`, and `sg_subnet_scoping` also need a peer BM in the same VPC (`FIREBIRD_PEER_BM_ID` + `FIREBIRD_PEER_KEY_FILE`) and skip, naming the missing peer, until one is configured. `sg_subnet_scoping` additionally needs the two BMs on different subnets. `FIREBIRD_SSH_USER` sets the login (default `ubuntu`).
- **Scoping without default-deny.** Rules have no priority and VPCs no default-deny group, so "allow only this node" cannot be expressed. The scoping checks apply a stateless DENY of ICMP echo requests aimed at one side and show that side stops answering while the other still does. While `sg_subnet_scoping`'s rule exists it blocks ICMP echo requests from every host on the peer's subnet, not just the peer; the check is opt-in (it needs a peer BM) and always deletes the rule.
- **Egress.** `stable_egress_ip_test` and the internet half of `traffic_validation` need internet egress from the tenant subnet; without it they fail rather than skip.
- `backend_switch_fabric` reads the flat `/topology/nodes/{node}` route (at the API root, not `/api/v1`) for the provisioned BM, or the first BM the tenant's topology lists.
- **Same-subnet pairs.** VPC firewall rules apply to traffic between subnets. `TrafficFlowCheck` and `SgNodeScopingCheck` therefore need the two BMs on different subnets; on a same-subnet pair the DENY rule is not exercised and both checks fail.
- **Cross-subnet pairs.** `sg_subnet_scoping`, and a cross-subnet answer from `traffic_validation` and `sg_node_scoping`, need both BMs provisioned on different subnets of one VPC; without such a pair, cross-subnet enforcement stays untested.
- **Topology.** `BackendSwitchFabricCheck` needs topology observation enabled on the deployment; where `GET /topology/nodes` reports `topology_status` `unknown` with empty tiers, it fails.
- The network config's header lists the checks that are not wired and why.

## Service accounts (control-plane, iam, security)

```bash
uv run isvctl test run -f isvctl/configs/providers/firebird/config/control-plane.yaml
uv run isvctl test run -f isvctl/configs/providers/firebird/config/iam.yaml
```

The run's credentials must be a tenant ADMIN: creating, rotating, and deleting service accounts (`/service-accounts`) and granting project roles require it. A service account is an OAuth 2.0 confidential client of the OIDC issuer; its client ID and secret, exchanged at `/auth/token` (`client_credentials`), are the access key / IAM user credentials. All three configs share [`scripts/common/service_accounts.py`](scripts/common/service_accounts.py) and one teardown script, [`scripts/iam/teardown.py`](scripts/iam/teardown.py). Every step records an account's or project's ID in its output, and logs it to stderr, as soon as it is created, so teardown deletes it even when the creating step fails later. Teardown reads each account and project before deleting it and refuses (fails on, without deleting) any not named with one of the prefixes below plus the 6-hex suffix, and never deletes the run's own project, so a wrong ID cannot remove the admin account or a real project.

- **Leftovers of killed runs.** A step killed mid-way never prints its IDs, so the first setup step of all three configs, `sweep_leftovers` ([`scripts/iam/sweep_leftovers.py`](scripts/iam/sweep_leftovers.py)), deletes them by name: service accounts named exactly `isv-cp-`, `isv-iam-`, `isv-sec-sa-`, `isv-sec-lp-`, or `isv-sec-audit-` plus the 6-hex suffix, and projects named `isv-lp-<hex>` (the least-privilege project B). Only those older than `FIREBIRD_SWEEP_MIN_AGE_HOURS` (default 6) go, so a concurrent run is never touched; a resource without a creation time, the run's own project, and every other name are left alone. It skips what it cannot list, reports what it deleted, and never fails setup.

- **Access key and IAM user.** `create_access_key` / `create_user` create the account and grant it VIEWER - the least-privileged predefined role - on `FIREBIRD_PROJECT_ID`. `test_access_key` / `test_credentials` log in with the new credentials, check `GET /users/me` names the account, and read the project with its token.
- **Disable = rotate.** Firebird has no "disable key" operation. `disable_access_key` rotates the secret (`POST /service-accounts/{id}/secret`) and reports the old secret `Inactive` only if `/auth/token` then refuses it; `verify_key_rejected` retries the old secret and fails if it still issues tokens. An identity provider whose client-secret rotation keeps the old secret valid for a grace period shows up as a failure of both checks, not a pass. The new secret is never emitted.
- **Tenants.** `list_tenants` / `get_tenant` read `GET /users/me` `tenants[]`. The target tenant is the `tenantId` of the run's project, which is also `check_api`'s `account_id`. Current API versions fill `tenants[]` for service-account principals too; an API that returns an empty list for a service account makes both steps skip (set `FIREBIRD_BEARER_TOKEN` to a user's token to cover them).
- Not wired: `create_tenant` / `delete_tenant` (tenants come from registration and operator verification; the tenant-management API is operator-only) and `s3_object_lifecycle` (tenants have no object storage).

## Security suite

```bash
uv run isvctl test run -f isvctl/configs/providers/firebird/config/security.yaml
# include CAP04-01 capacity grouping:
uv run isvctl test run -f isvctl/configs/providers/firebird/config/security.yaml --capability bare_metal
```

- **SEC03-01** `sa_credential_test` creates an account and shows its token resolves to it (`credential_source: long_lived_key`, the secret; the token is short-lived).
- **SEC01-01** `oidc_user_auth_test` uses the run's own JWT: the issuer's discovery document and JWKS must serve its signing key, the token must be accepted at `/users/me`, and tampered tokens must get 401. A tenant cannot get validly signed tokens with a wrong issuer or expiry, so those are forged by editing claims; they fail signature verification, and the output says the claim checks are not isolated (`claim_rejection_evidence: signature`). A tenant cannot mint a validly signed token for another audience either, and a forged one would only prove the signature check, so `wrong_audience_rejected` is not probed: it is reported failed as not supported (`supported: false`), `OidcUserAuthCheck` fails on it alone, and the step succeeds on the other subtests.
- **SEC04-01 / SEC04-02** `least_privilege_test` grants a new account VIEWER on the run's project (A) and creates a throwaway project (B): the account is denied on A before the grant and allowed after it, denied on B, and denied a BM power-on, a filesystem create, and a VPC create on A. The API checks permissions before looking up the target or validating the body, so a denial is 403; the probes target a nonexistent BM and send an invalid (empty) name, so they cannot change anything even if allowed. Teardown deletes the account and project B.
- **SEC08** `audit_logging_test` creates an account and finds its CREATE event in `GET /audit`. Firebird audit events have no source IP, user agent, or region, so `AuditLogEntryCheck` fails on exactly those three subtests (reported `supported: false`). `AuditLogRetentionCheck` is observed retention, as for the serial console: an audit event in the year ending 30 days ago, since no retention policy is exposed. Skips when the audit API is not enabled.
- **SEC13-02** `insecure_protocols_test` runs the shared raw-socket prober (`providers/shared/insecure_protocols_test.py`) against the API host: SSLv3/TLSv1.0/TLSv1.1 ClientHellos and plain HTTP on :80. The prober counts timeouts as refusals, so the endpoint must also answer a TLSv1.2 ClientHello, or the step fails as inconclusive.
- **CAP04-01** `capacity_reservation_grouping` treats the tenant BM pool (`GET /compute/bms`) as the reservation: there is no reservation object, so `reservation_id` is the tenant ID, and a BM is pinned when it carries that tenant ID. Isolation here is the API's server-side tenant filter on that listing, not an observed property - other tenants' BMs are never visible (`cross_tenant_observable: false`).
- The config header lists the checks that are not wired and why. The BMC and switch-plane checks are gaps, not `provider_hidden`.

## Storage suite

```bash
uv run isvctl test run -f isvctl/configs/providers/firebird/config/storage.yaml --capability bare_metal \
  --junitxml reports/storage/junit-validation.xml
# with the mount checks, on an already-provisioned BM:
BM_INSTANCE_ID=bm.xxx BM_KEY_FILE=/path/to/bm-key \
  uv run isvctl test run -f isvctl/configs/providers/firebird/config/storage.yaml --capability bare_metal
```

Needs `FIREBIRD_PROJECT_ID` plus `FIREBIRD_CLIENT_ID` / `FIREBIRD_CLIENT_SECRET` (or `FIREBIRD_BEARER_TOKEN`) with filesystem create, update, and delete on the project; `FIREBIRD_API_BASE` and `FIREBIRD_SWEEP_MIN_AGE_HOURS` are optional. The mount checks need `BM_INSTANCE_ID` / `BM_KEY_FILE` (and optionally `FIREBIRD_SSH_USER`, default `ubuntu`, and `FIREBIRD_WEKA_MOUNT_OPTIONS`, default `net=udp`); without them they skip with "no BM configured for mount checks" and the API-only checks still run. `--capability bare_metal` enables the mount checks (all but HSS13-01 require it); without it they are filtered out. The JUnit report goes to `--junitxml` (default `_output/junit-validation.xml`); `pytest-output.log` and `test_catalog.json` are written to `_output/` under the working directory.

The Filesystem API (`/projects/{p}/storage/fs`) provisions filesystems in the tenant's organization on the parallel filesystem: every create, resize, and delete is observed through the API, where the Operation completes and the readback is READY.

- **Filesystem safety.** Every filesystem the run creates is 1 GiB (the platform's minimum; `live_expansion` grows its own to 2 GiB) and named `isv-fs-<run_id>-<role>`, where `setup` mints the run ID. The step that creates a filesystem deletes it on every path, and a failed delete fails that step. `teardown` then deletes anything still named with the run's prefix, including the StorageProvider shim's filesystem (the check only logs a failed `delete_volume`). `sweep_leftovers` deletes `isv-fs-<hex>-*` filesystems older than `FIREBIRD_SWEEP_MIN_AGE_HOURS` (default 6) left by killed runs. Every create, resize, and delete checks the filesystem's name and refuses anything not named `isv-fs-*` (a delete reads it first), so the tenant's own filesystems are never touched, even by a wrong ID. Each creating script's `--timeout` covers its work and its cleanup, with every delete sharing one deadline (as in `teardown` and `sweep_leftovers`), and stays under the step timeout, so a failure path cannot outlast the step.
- **Mount prerequisites.** The mount checks run on a BM that is already provisioned and RUNNING (for example one a bare_metal run kept with `BM_SKIP_TEARDOWN=true`), reachable over SSH from the runner, with passwordless `sudo`, `python3`, and `curl`, and a route to the filesystem service named by the API's `storageEndpoint`. They run one storage run per BM at a time. Nothing but the parallel filesystem client is installed; the I/O probes are plain Python sent over SSH, so no `fio` is needed.
- **Client install.** `setup_mount` installs the parallel filesystem client only when `mount.wekafs` is missing, and logs the version. It trusts the installer served by the storage endpoint the authenticated API returned, executed as root: `https` on that endpoint's own host:port is tried first (downloaded, then run as root under a timeout), falling back to the API-returned URL only if `https` fails; `ISV_WEKA_INSTALL_URL` overrides both with a single URL to use instead. The client is left installed; later runs reuse it. The first mount builds the client drivers and starts its container, which takes a few minutes.
- **Mount token.** `GET .../storage/fs/{id}` also returns `authCredentialsBase64`, a base64 client `auth-token.json` for the tenant's filesystem organization. Only the steps that mount a filesystem read it; they hold it in memory and send it to the BM over SSH stdin, where a fixed program checks it decodes to the auth-token shape (printing key names only) and writes it to a suite-owned file, `/root/.weka/isv-<run_id>.json` (0600, in a 0700 directory) - never the tenant's own `/root/.weka/auth-token.json`, which this provider never writes to, reads, or deletes. Mounts pass `auth_token_path=<that file>`, and every `weka` CLI call sets `WEKA_TOKEN` to it, so nothing ever falls back to (or could overwrite) a token the suite did not write itself. The credential never appears in a command line, a log, a local file, or step output, and error texts that could echo remote output are redacted. Every other script keeps only the `filesystem` object, and the shim reads only the collection. `teardown` deletes the run's own token file; `sweep_leftovers` deletes any leftover `isv-*.json` token whose run is no longer mounted. The token's user can be a read-only organization user: that is enough to mount, read, and write, and to list filesystems, containers, and audit state, but not to set a quota or enable audit, so those subtests fail with the role error the mount reports (the checks name the token's role). The filesystem's name on the mount is the API name; `setup_mount` fails rather than guess when the token does not list it.
- **Mounts.** `setup_mount` creates `isv-fs-<run_id>-mount` (1 GiB), confirms the token lists it under its API name, mounts it with `mount -t wekafs -o net=udp,auth_token_path=<isv- token> <backend>/<name> /mnt/isv-<run_id>`, and writes, reads back, and removes a probe file. If the install or mount fails, the step reports the (redacted) error, removes its token best-effort, and every mount check fails with the error rather than skipping; the API-only checks still run. `live_expansion` and `home_directory_storage` mount their own filesystems at `/mnt/isv-<run_id>-<role>` and unmount them before deleting; `live_expansion`'s background I/O writer is staged under a fresh root-only (`sudo mktemp -d`, 0700) directory under `/root`, never a predictable `/tmp` path. `teardown` unmounts every `/mnt/isv-<run_id>*` mount and removes those directories before any filesystem delete; `sweep_leftovers` unmounts `/mnt/isv-*` mounts of `isv-fs-*` filesystems it is about to delete or that no longer exist. No other mount point is ever touched.
- **Live expansion.** The API records the requested capacity when it accepts a resize, so a readback of the new size alone is not evidence of a resize. `capacity_expanded` requires the filesystem readback to show the requested size and `/storage/fs/status` to show the expected allocation increase; two agreeing status reads are required to rule out transient values (the allocation reported by `/storage/fs/status` can lag a delete by a few seconds, so the baseline read polls). This also means the create's own allocation, if it lands late, cannot pass for the resize; another project's create or delete in the same tenant during the step can shift it. `metadata_consistent` is control-plane evidence (same ID, name, and creation time, READY). With a BM, the filesystem is mounted during the resize: `inodes_expanded` needs the inode count the client reports to grow, and `io_uninterrupted` needs a background writer (write, fsync, read back every 0.1 s) to see no error and no gap over 30 s from before the resize until after it settles. Without a BM those two are reported failed as not supported. The step succeeds on the API-observable subtests.
- **What the mount checks assert.** HSS07-01: the API readback and the mount probe. HSS02-01: O_DIRECT bandwidth (parallel writers, then readers; the lower rate) and random 4 KiB O_DIRECT read IOPS against 1000 MB/s and 50000 IOPS; the Filesystem API has no QoS class, so these are the suite reference minimums. HSS12-01: the filesystem's quotas are per directory, so the uid and gid subtests fail as not supported, and the directory quota is set with `weka fs quota set` and probed past its soft and hard limits (a token role that cannot set quotas fails those subtests with the role error the mount reports). HSS13-01: the Filesystem API has no root-squash setting, so the toggles fail as not supported; the owner of a root-created file decides `root_squashed` / `root_unsquashed`. HSS14-01: exclusive, shared, and contended `flock` from separate processes. HSS15-01: the filesystem's audit state (`weka audit fs status`); audit records are not exposed through the tenant API, so the record-content subtests are unsupported. HSS18-01: the client container's address count (`path_count`), every backend server UP and reachable from the BM (`server_count`); failover is not tested (it needs a path or server taken down). DIR01-01: on its own filesystem, the mount reports the requested capacity, reports the new one after a resize, and refuses a write past it with ENOSPC. DIR01-02: files written by two uids and gids sum exactly per owner.
- **StorageProvider shim.** [`scripts/storage/firebird/api.py`](scripts/storage/firebird/api.py), declared in [`config/storage-provider-manifest.yaml`](config/storage-provider-manifest.yaml): `health_check` lists filesystems, `create_volume` / `delete_volume` create and delete a filesystem, `get_tenant_quota` is `/storage/fs/status` (the tenant is the project's). The manifest names no `tenant_id`, since a static file cannot know the project's tenant.

## Image registry

```bash
uv run isvctl test run -f isvctl/configs/providers/firebird/config/image-registry.yaml
# include the BM install (creates a network unless FIREBIRD_SUBNET_ID is set):
uv run isvctl test run -f isvctl/configs/providers/firebird/config/image-registry.yaml --capability bare_metal
```

- **Upload.** Images are uploaded through the API's multipart upload routes (`POST /compute/images/{project}/uploads`, raw `PUT .../uploads/{id}/parts/{n}`, `POST .../complete` with a SHA-256 checksum, then `GET .../uploads/{id}`); `upload_image` reads the registered image back. An upload that fails before it finishes is aborted. When those routes are unavailable the step emits a structured skip, and `upload_image`, `crud_image`, `install_image_bm`, and `teardown_image` all skip.
- **Formats.** The API inspects the file at finish and accepts qcow2 or raw whole-disk images (with an MBR or GPT). The suite's default `.vmdk` is refused, so the config defaults to Ubuntu's 24.04 cloud image (qcow2); override with `FIREBIRD_IMAGE_URL` / `FIREBIRD_IMAGE_FORMAT`.
- **Contract fields.** `storage_bucket` is the scope the image is stored under (the project) and `disk_ids` holds the upload's `objectId`, the reference to the stored file.
- **CRUD.** `crud_image` runs create (upload), get, list, and delete on a 1 MiB raw probe image of its own, so it never touches the image the BM install uses (the API refuses to delete an image a BM references).
- **BM install.** `install_image_bm` runs the bare_metal launch path (`scripts/common/provision.py`) with the uploaded image and a key generated for the run: an AVAILABLE BM is attached and provisioned, must reach RUNNING and answer SSH, and must report the uploaded image. It always provisions (a BM kept with `BM_INSTANCE_ID` proves nothing about a custom image). Teardown deprovisions it and detaches only what it attached, deletes the network `create_network` created, and only then deletes the image. With the upload service off, a `--capability bare_metal` run still creates and deletes the network, since steps cannot be conditional.
- Not wired: `crud_install_config` / `install_config_bm` (no install-config resource; user-data is supplied per provision) and the VM steps.

## Bare-metal coverage notes

- **Stable IPs (STG03-01).** A BM's subnet address is reserved when it is first provisioned and outlives a deprovision (teardown releases it only when the run attached the BM's subnet), so `query_stable_ips` covers the provisioned BMs (RUNNING or STOPPED) on a subnet; an attached AVAILABLE BM may or may not hold an address and is out of scope.
- **Fleet-capacity report** (`GET /reports/ncp/fleet-capacity`) backs `query_governance_metrics`, `query_fleet_inventory`, and `query_host_health`, and is optional: when the route answers 404 or 501 all three emit a structured skip. The report holds only the calling tenant's nodes, so the metrics and records are tenant-scoped, not site-wide.
  - Governance buckets: Delivered = every row; Healthy = `healthState` HEALTHY; Reserved = `capacityState` In Use or Reserved; Active = `capacityState` In Use.
  - Host health is one coarse classification per node with its observation time - no probe IDs or per-component alerts exist. An UNHEALTHY node is reported with one alert standing for that classification (so the check fails it); UNKNOWN counts as no report.
- `query_resource_discovery` polls the tenant BM pool (`GET /compute/bms`) twice. ALLOCATED and PROVISIONING BMs are listed but not counted as discovered (hardware registration may not have finished).
- `query_bmc_kernel_logs` reads the BM's serial-log history (`from`/`to`, last 24 hours); `query_maintenance_events` reads open events (ACTIVE + REQUESTED) and skips its check when there are none; `query_repair_history` groups all events, including cleared ones, per BM. The NCP repair report is not used because its rows carry no node ID.
- `query_ib_tenant_isolation` lists the project's IB partitions and skips when the IB partition API is not enabled. A tenant sees only its own partitions, so the step shows each P_Key is real, not the default partition, and owned by this tenant - but not that no other tenant shares it (`cross_tenant_observable: false`).
- `query_node_health_agents` reuses the shared SSH reference against the provisioned BM when `FIREBIRD_HEALTH_AGENT_CHECK=true`. The fleet size it must cover is the project's in-use GPU nodes from the fleet-capacity report, so it fails (not passes) when other GPU BMs are running in the project, when the BM has no GPUs, or when the report is unavailable. It passes only if the image runs a GPU health agent (GPUd, NVSentinel, ...).
- Not wired, because the tenant API exposes nothing that answers them honestly: `query_health_aggregation`, `query_ib_keys` (no M_Key), `query_sanitization`, `query_topology` (no rack or enclosure), `query_oob_health`, `query_attestation`, `query_key_access`, `query_serial_numbers`, `query_switch_firmware`, `query_retirement_notices`, `report_node_repair`, `return_node_maintenance`, `return_rack_maintenance`, `request_host_replacement`, `query_planned_notifications`, `query_failure_notifications`, and the operator-side `verify_ingestion` / `check_dpu_health` / `check_dpu_network`.
- `topology_placement` is not wired: the API exposes node topology but has no customer placement-group operation, so `BmTopologyPlacementCheck` skips.
- `reinstall_instance` (deprovision + provision) is implemented but `skip: true` by default because it performs two full OS installs.
- `SerialConsoleRetentionCheck` queries the year ending 30 days ago and passes only if the BM has a serial log record in it. The API does not expose the configured retention policy, so the reported retention is the observed age of that record.
